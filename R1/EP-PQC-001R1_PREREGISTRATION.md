## 1. Why R1 exists (honest failure diagnosis of EP-PQC-001)

EP-PQC-001 produced an **official verdict of PARTIAL (safety-PASS, classification deviations)**:
`decision_match = 23/24`, `reason_match = 22/24`, **False_ALLOW = 0**, **safety-invariant
violations = none**, boundary crossings = exactly the four expected-ALLOW cases
(`PQC-01, PQC-09, PQC-11a, NC-00`). That original result is preserved verbatim in
`results/scored_results.json` and is **NOT edited, reclassified, or overwritten** by R1.

The two deviations were both **SAFE** (the prohibited operation was blocked in every case) and
both traced to **my test-design choices in the EP-PQC-001 preregistration — not to the
enforcement engine**:

- **PQC-04** — I preregistered expected `HOLD / EVID_ALGORITHM_CLAIM_MISMATCH`, but the requester
  I chose (`svc-tls-frontend`) was **not** the custodian of `KEY-RSA2048`. The authority stage
  therefore correctly fired first (`AUTH_CUSTODY_MISMATCH → DENY`) and short-circuited before the
  evidence stage could exercise the algorithm-mismatch path. The operation was still blocked;
  the case simply failed to *isolate* the dimension I intended to test.
- **PQC-12** — I preregistered expected `HOLD / EVID_NONCE_BINDING_MISMATCH`, but the cross-request
  replay I constructed is caught **first** by the request-binding control
  (`EVID_REQUEST_BINDING_MISMATCH`), which is the dominant anti-replay invariant and runs before
  nonce-binding. Same decision (HOLD), adjacent reason code.

Both are **goalpost-preserving** facts: the engine behaved correctly and conservatively. R1 fixes
the **test design**, not the engine, and adds a case that isolates the nonce-replay control the
original PQC-12 was meant to (but did not) exercise.

## 2. What R1 changes (test design only — engine untouched)

- **R1-FIX-1 (PQC-04):** requester changed to `svc-vpn-gw`, the authorized custodian of
  `KEY-RSA2048`. Authority now PASSES, so the **evidence** stage independently derives the
  artifact as RSA-2048 and fires `EVID_ALGORITHM_CLAIM_MISMATCH` against the ML-KEM-768 claim.
  Expected: `HOLD / EVID_ALGORITHM_CLAIM_MISMATCH`.
- **R1-FIX-2 (PQC-12):** expected primary reason corrected to `EVID_REQUEST_BINDING_MISMATCH`,
  the honest detection for cross-request replay. Decision unchanged (`HOLD`).
- **R1-ADD (PQC-17a / PQC-17b):** explicit **nonce-consumption replay**. `PQC-17a` is a valid
  request that ALLOWs and **consumes** nonce `n17`. `PQC-17b` re-submits the **identical signed
  evidence to the same `request_id`**, so request-binding passes and the consumed-nonce control
  must fire: expected `HOLD / EVID_NONCE_REPLAY`. This isolates the anti-replay dimension PQC-12
  was intended to cover.

No change is made to `impl/ep_pqc_core.py`, to the ExecutionProof invariants, or to the policy
files `policy/EP-PQC-POLICY-001-A.json` / `policy/EP-PQC-POLICY-001-B.json`.

## 3. Invariants under test (unchanged from EP-PQC-001)

1. Incomplete contract ⇒ **HOLD**
2. Authority FAIL ⇒ **DENY**
3. Authority PASS + Evidence FAIL ⇒ **HOLD**
4. Authority PASS + Evidence PASS + Constraint FAIL ⇒ **HOLD**
5. All stages PASS ⇒ **ALLOW** (and only then does the protected ML-KEM encapsulation run)
6. No cached permission — every request is re-verified from scratch; nonces are single-use.

The **safety ordering** of error severity is preserved: a **False ALLOW** (a prohibited
operation crossing the boundary) is the worst outcome and is the sole hard failure condition for
the safety verdict.

## 4. Preregistered pass / fail rule (identical to EP-PQC-001; no goalpost change)

- **SAFETY PASS** iff `False_ALLOW == 0` **and** no non-ALLOW expectation crosses the execution
  boundary.
- **EXACT-CLASSIFICATION PASS** iff every case matches on **both** decision and primary reason
  code.
- **VERDICT = PASS** iff SAFETY PASS **and** EXACT-CLASSIFICATION PASS.
- **VERDICT = PARTIAL** iff SAFETY PASS but not EXACT-CLASSIFICATION PASS (deviations preserved
  and reported individually).
- **VERDICT = FAIL** iff not SAFETY PASS (any False ALLOW or any boundary violation).
- Negative controls must each change exactly one dimension and flip only the expected stage.

R1 **targets** a clean `PASS` (26/26 on both decision and reason, 0 False ALLOW). Whatever the
blind runner actually produces will be reported verbatim — a PARTIAL or FAIL would be preserved,
not massaged.

## 5. Blinding (procedural, honestly disclosed)

- The generator (`generate_cases_r1.py`) writes `challenges.json` (NO labels) and a **separate
  sealed** `answer_key.sealed.json`.
- The runner (`run_experiment_r1.py`) reads **only** challenges + policy + the authority public
  key. It never reads the sealed answer key.
- The scorer (`score_r1.py`) compares only AFTER the run.
- **Honesty caveat:** blinding is *procedural*, performed by a single author (Derek's agent), not
  an independent third party. This is a software-only simulation — no HSM/TPM, no live TLS
  handshake, no production key-management system. The experiment does **not** prove the security
  of ML-KEM or ML-DSA; it tests whether the ExecutionProof gateway independently verifies real
  cryptographic artifacts and physically blocks non-ALLOW operations.
